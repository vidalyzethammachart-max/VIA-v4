# Cloud video frame extraction — 2026-10-30

Status: local patch; not deployed or verified on Render/n8n.

The reported HTTP 422 `invalid_video` message is generated by the backend's
ffmpeg wrapper, before Gemini inference. Frame extraction is fatal, while audio
extraction failure is handled separately. The old message cannot distinguish a
deadline from a decoder exit or host termination. It does not prove which event
occurred on Render. Raising n8n's HTTP timeout alone cannot fix that failure.

## Smallest change

- Replace the full-clip `fps` decoder pass with six sequential input seeks,
  sampling at 0, 1/6, 2/6, 3/6, 4/6 and 5/6 of the duration by default.
  The existing configurable frame count still applies.
- Select the first actual video stream with `0:V:0`, excluding attached art.
- Use one decoder, filter and encoder thread per sample. Bound both image
  dimensions to 1024 pixels while preserving aspect ratio. Extraction as a whole
  retains a ten-minute deadline, rather than allowing ten minutes per sample.
- Preserve full audio extraction, the provider, the response envelope and the
  existing number of image inputs. No new package or cloud service is needed.
- Distinguish process timeout, host termination and nonzero decoder exit in the
  error message. Log stage, exit code, signal and timeout flag without media
  contents, paths, signed URLs or credentials. A signal alone does not prove OOM.

Input `-ss` seeks to a nearby seek point and accurate seeking decodes the
remaining interval; it avoids decoding the entire preceding clip. See the
[official ffmpeg documentation](https://www.ffmpeg.org/ffmpeg.html).
Long GOPs and poorly indexed containers can reduce this benefit.

## Local evidence

Using the original `2 Introduction Negotiating for Value Creation.m4v`
(342,328,931 bytes, 272.08 seconds), without download or AI inference:

| Frame extraction | Wall time |
| --- | ---: |
| Original full-clip fps command | 9.017 s |
| Sequential input seeks | 1.157 s |

One local comparison, approximately 7.8× faster; six nonempty JPEGs produced.
This is not a cloud benchmark, peak RAM measurement, billing estimate or total
pipeline timing. The first sample moves to the start of the clip; the output
remains sparse evidence rather than a continuous review.

The regression test generates six differently colored sections in a portrait
video, checks chronological sample contents and the image dimension bound, and
checks that invalid input reports a decode failure without leaking its path.
Existing endpoint tests exercise real ffmpeg with simulated provider responses.

## Cloud verification still required

Deploy this patch to the existing Render Free service; its recorded auto-deploy
setting is off. Keep Analyze Video retries off and allow the backend work within
the HTTP/workflow deadlines. After confirming no analysis is active, retry only
the confirmed failed analysis once, then inspect its execution, callback and
generated documents. If it fails, use the new ffmpeg diagnostics to distinguish
timeout from exit/termination before changing hosting or repeating inference.

This patch reduces media decoding work. It does not reduce the intended image
count, shorten the audio, guarantee a smaller Gemini bill, or create a durable
result cache. Render Free loses local caches on sleep/restart and has usage and
traffic limits; see [Render Free documentation](https://render.com/docs/free).
No paid plan or billing configuration was changed.
